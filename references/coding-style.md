# 编码纪律：写与改

适用：任何涉及代码变更的动作——写代码、改代码、重构、代码审查、脚本与配置优化，覆盖快路径、bugfix 压缩路径与完整工作流阶段④。

核心原则：易读、易懂、易维护。优先考虑可读性，而不是追求代码简短；每次变更最小化、可追溯，按成功标准验收。

## 开工纪律（每次代码变更前）

- **总纲：每次执行任务遵循 Karpathy guidelines 四原则**：开工前调用 Skill `karpathy-guidelines` 逐条对照执行。Karpathy 状态全程只记录两种：`loaded`（已加载并对照执行）或 `unavailable_reported`（不可用且已显式报告）。技能不可用时在汇报中如实标注，不阻塞最小流程，按本文件其余纪律执行。
- 开工前定义可验证的成功标准，把任务转化为可判定达成的判据；多步任务列出计划，每步标注验证点。
- 优先复用项目已有工具、模式与封装，确认无法满足再引入新依赖。
- 修改时最小化变更，避免影响无关代码；未明确要求不主动重构、优化或扩展功能。
- 每行变更须可追溯到已确认的用户请求、规格或工单；自己产生的孤儿代码必须清理，既有死代码标注后提请用户决定。
- Debug：先定位根因再修改，不基于猜测连续改代码。

## 写法纪律

1. **减少封装**：不要过度拆分函数，不要为了复用而抽取大量辅助函数。只有职责独立、确实有复用价值，或者包住了确实复杂的逻辑、代表一个能起清楚名字的概念，才单独封装；只用一次的逻辑不要先抽出来。
2. **减少修饰和包装**：避免不必要的装饰器、类、继承、静态方法、属性包装和上下文管理器。只保留确实有必要的设计。
3. **减少嵌套**：优先使用提前返回（Early Return），减少多层 if、try 和 with 嵌套，让主要执行逻辑尽量保持扁平。
4. **主函数只写正常流程**：校验与细节放到它下面的小函数里，主函数读起来是一条直线。
5. **优先使用直观语法**：多使用普通的 if/else、for、try/except/finally，少使用复杂的推导式、三元表达式、隐式技巧和过于简洁的语法。
6. **避免过度压缩代码**：宁可多写几行，也要把执行步骤和逻辑关系表达清楚。不要为了减少代码行数牺牲可读性。
7. **注释使用中文，只写不明显的**：所有注释和 Docstring 使用简洁、准确的中文，遵循项目既有语言约定。注释重点解释代码的目的、设计原因和非显然的约束（“为什么”而非“做什么”），不给显而易见的代码写注释，不简单重复代码本身。
8. **命名清晰**：变量、函数和类的名称应尽量直观，让读者不需要反复跳转就能理解其作用。

## 改动纪律（行为保持）

1. **保持原有功能**：优化代码结构时，不随意删减功能、改变业务逻辑、修改接口或改变异常处理语义。
2. **谨慎处理复杂机制**：涉及异步执行、上下文传播、异常处理、资源释放、并发和数据安全时，优先保证正确性，不为简化代码而破坏原有行为。
3. **控制优化范围**：不引入不必要的第三方依赖，不为形式上的架构整洁增加抽象层。
4. **易踩的四条边界**（动了就是行为变更，要么不动，要么在交付里单列风险）：
   - **异常语义**：合并 except 分支、放宽捕获范围、把异常改成返回值，都属于改变行为。
   - **资源释放**：删掉 with 只为了少一层缩进会漏释放文件、锁和连接；提前返回要在返回前完成清理。
   - **异步与上下文**：去掉 await、改写上下文管理器、把并发逻辑串行化，会改变执行顺序与上下文传播，属于高风险改动。
   - **公共接口**：重构私有实现可以自由调整，公共函数签名、返回结构、错误码一旦变化必须显式声明。

## 输出要求

- 先给出完整的优化后代码，不要只给局部片段。
- 代码中的注释和 Docstring 全部使用中文。
- 再简要说明主要修改点及修改原因。
- 对可能影响原有功能或存在兼容性风险的修改，单独指出。
- 不要为了展示设计模式而增加不必要的复杂度。

## 最终目标

让一个刚接触该项目的开发者，也能按照代码从上到下的顺序，理解每一步在做什么、为什么这样做。

## 交付前自检

- 开工前已定义可验证的成功标准，每行变更可追溯到已确认的请求、规格或工单。
- 交付的是完整文件或完整函数，不是省略号片段。
- 注释与 Docstring 全中文，解释目的与非显然的原因，不复述语句本身。
- 新增函数至少满足其一：会被复用、封装了确实复杂的逻辑、代表一个能起清楚名字的概念；主函数读起来是一条直线。
- 修改点清单与代码一一对应，风险项已单列。
- 没有为风格改动引入新依赖或新抽象层。
- 原有功能、接口、异常语义未被改变；如已改变，已显式声明。
- 完成后已按成功标准逐项核验（正常路径、边界情况、异常路径），贴证据而非泛泛自检。
