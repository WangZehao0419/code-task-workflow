# 五阶段操作卡

每张卡包含：目标 / 动作序列 / 调用指令 / 交接物 / 出口 checklist / 常见失败。主文件 SKILL.md 的路由表按阶段编号索引到本文件。手动型技能（磁盘协议调用）的路径表见 SKILL.md 第 4 节。

## 阶段① 问清需求

**目标**：把"要做什么"聊到没有关键歧义——谁会用、怎样算做完、失败怎么办、这次不做什么。

**动作序列**

1. 先自查：列出悬而未决的问题，标出哪些能从代码、文档、现有测试中找到答案 → 自己读代码回答，**不把查资料变成问用户**。
2. 交互效果光聊定不下来（布局、流程、手感）→ 调用 Skill `prototype` 做一个可运行的小原型，体验后再决定。
3. 调用 Skill `grilling` 对剩余问题逐条访谈；涉及领域词汇、边界概念 → 调用 Skill `domain-modeling` 沉淀 ADR 与词汇表。
4. **方案调研**（新项目 / 新功能 / 新独立模块时执行；bug 修复与既有架构内的小改动跳过）：先检索再写码。用 GitHub 搜索与网络搜索，以已澄清的需求为关键词，找可直接使用或二次开发的开源项目。对候选逐项分析：是否仍在维护（最近提交 / release / issue 活跃度、是否归档）、部署是否简单、哪些功能可直接复用、哪些地方需要修改、License 是否与本项目兼容。产出三选一建议——**直接使用 / 基于改造 / 从零开发**——并给出最快跑通 MVP 的路径。**建议与依据交用户拍板**（hard gate，见 SKILL.md 第 5 节）。检索工具不可用时如实告知、标注"未做方案调研"，由用户决定继续或停止。既有架构内的小型功能增强，调研可在 1–2 次检索内收口、无需展开完整候选分析（见 SKILL.md 第 3 节流程压缩）。
5. （用户明确要求完整版时）Read `grill-with-docs` 的 SKILL.md（路径见 SKILL.md 第 4 节）按其协议执行。

**调用指令模板**

> 调用 Skill 工具（skill: `grilling`），围绕以下未决问题逐条访谈用户：<清单>。代码可答的问题已自行回答，依据见：<文件/行>。

**交接物**：澄清记录（问题 → 答案 → 依据）；方案调研记录（候选项目 → 维护 / 部署 / 复用点 / 修改点 / License 分析 → 三选一建议）；领域词汇表与 ADR（若走了 domain-modeling）。

**出口 checklist**

- [ ] 谁会用、使用场景明确
- [ ] 成功标准（怎样算做完）明确
- [ ] 失败路径（权限、空状态、异常、重试）明确
- [ ] 范围边界（这次不做什么）明确
- [ ] 用户对以上逐条确认
- [ ] 新项目 / 新功能：复用决策经用户确认

**常见失败**：一路点头接受 AI 的建议；把代码能答的问题拿去问用户；跳过方案调研从零重造现成轮子（Token 与时间白费）；不查维护状态与 License 就引入外部项目；为省 Token 强行套用不合需求的项目；未定义失败路径就进入规格。

## 阶段② 写成规格

**目标**：把已确认的讨论固化为规格——记录用户行为、约束、测试方式、范围外。不再访谈，不发明新需求。

**动作序列**

1. Read `to-spec` 的 SKILL.md（路径见 SKILL.md 第 4 节），按协议执行。
2. 探索代码库现状（若阶段① 尚未充分探索）；全文使用项目领域词汇，尊重既有 ADR。
3. 规划测试 seam：优先既有 seam，能用高层不用低层，新 seam 提在最高处；**seam 方案交用户确认**（hard gate，见 SKILL.md 第 5 节）。
4. 按模板写规格并发布：tracker 配置存在 → 按 tracker 发布并打 ready-for-agent 标签；否则本地写 `docs/specs/<slug>.md` 并注明本地文件模式。

**规格模板（四节 + 问题/方案）**

```markdown
## Problem Statement   # 用户视角的问题
## Solution            # 用户视角的解法
## Constraints         # 约束：技术、兼容、依赖
## Test Plan           # 测试方式：seam、用例、验收标准
## Out of Scope        # 这次不做什么
```

**出口 checklist**

- [ ] 四节齐全，内容全部来自已确认的对话
- [ ] seam 方案经用户确认
- [ ] 已发布（tracker 或本地路径），路径已告知用户

**常见失败**：规格夹带访谈没确认过的新决策；seam 越切越碎；忘记声明本地文件模式。

## 阶段③ 拆小任务

**目标**：规格 → 可独立演示的纵向切片，依赖显式，完成可判定。

**动作序列**

1. Read `to-tickets` 的 SKILL.md（路径见 SKILL.md 第 4 节），按协议执行。无 tracker 时用其本地文件模式：`.scratch/<slug>/issues/<NN>-<slug>.md`，每票一个文件，Blocked by 以文本声明。
2. 按"用户行为"切片，不按技术层切片：表单+接口+存储+成功提示是一票，不是四票。
3. 找 prefactor 机会——"先让改动变容易，再做容易的改动"，但每张 prefactor 票同样要能验证。
4. **工单清单与依赖关系交用户确认**（hard gate）。

**拆分检查三问**：每票能演示吗？依赖明确吗？完成可判定吗？

**出口 checklist**

- [ ] 每票独立可演示
- [ ] Blocked by 显式声明，依赖链成立
- [ ] 每票有可判定的完成标准
- [ ] 用户确认拆分粒度与顺序

**常见失败**：按技术层拆票（前端票 / 后端票）；依赖没写导致并行踩空；一票大到无法演示。

## 阶段④ 实现与验收

**目标**：一票一票实现，每票都有真实验证证据，验收后才算完成。

**动作序列（单票）**

1. Read `implement` 的 SKILL.md（路径见 SKILL.md 第 4 节），按协议实现该票。
2. 调用 Skill `tdd` 在已确认的 seam 上测试先行。
3. 项目配有类型检查时定期运行（无配置则跳过）；定期跑单文件测试，整票完成跑一次完整测试套件。
4. 调用 Skill `code-review`（Standards + Spec 两轴），处理发现的问题或说明不处理的原因。
5. 请求人工走查（hard gate）：告诉用户怎么跑、操作什么、预期看到什么。
6. 汇报验收证据：真实测试输出（引用原文，不编造）、截图或 PR 描述、**未验证项显式列出**。

**并行升级**：满足 SKILL.md 第 6 节全部条件后，Read `implement-spec` 的 SKILL.md（路径按 SKILL.md 第 4 节 的模式）按协议执行（worktree + 集成分支 + 实现者子代理 + context pointer 沟通）。

**出口 checklist（每票）**

- [ ] 测试真实通过（引用输出原文）
- [ ] code-review 完成且问题已处理或说明
- [ ] 用户走查确认
- [ ] 未验证项已列出

**常见失败**：测试通过就单方面宣称"完成"（没走查）；未经确认就并行；编造测试输出。

## 阶段⑤ 复盘改进

**目标**：从执行记录里找过程问题，让下次少走弯路。任务成功也值得复盘。

**动作序列**

1. Read `retro` 的 SKILL.md（路径见 SKILL.md 第 4 节），按协议执行（读会话记录 / 执行日志）。
2. 按类别找候选问题：

| 遇到的问题 | 怎么改 |
|---|---|
| 查找费劲 | 补清楚入口、目录说明与相关文档 |
| 参考过时 | 更新或移除误导 agent 的旧资料 |
| 重复犯错 | 能自动判断的规则变成测试、lint 或 CI 检查 |
| 需要判断 | 把有证据的经验写进项目规范 |

3. 改进候选按严重度排序交用户取舍。
4. 原则：**用真实执行记录改流程，不靠堆更多提示词。**

**出口 checklist**

- [ ] 至少检查了导航、自动化检查、编码规范三类
- [ ] 每个改进项有明确落点（哪个文件 / 哪个检查 / 哪份规范）
- [ ] 用户确认取舍

**常见失败**：复盘变成表扬会；改进项没有落点；把需要判断的经验硬塞给自动化检查。

## 降级操作卡：外部技能缺失时的内联最小流程

> 触发条件（见 SKILL.md 第 7 节第 3 条）：某阶段技能文件缺失、损坏，或通道 B 协议路径（按 SKILL.md 第 4 节 `<skills-root>` 规则解析）解析失败。此时不调用对应外部技能，按本卡以本技能内联指引跑通五阶段最小流程。

**目标**：在专项技能不可用时仍跑通"访谈 → 规格 → 拆票 → 实现+验证 → 复盘"，保住六处门控与验收证据底线，产出质量不低于本卡"交接物"列出的质量下限。

**动作序列**

1. 先标注：汇报首行固定为"已降级（缺失：<技能名 / 路径>）"，并列出缺失清单与受影响阶段，不隐藏降级事实。
2. 按阶段内联最小步骤推进：
   - ① 问清需求：自行逐条访谈用户，问清"谁会用 / 怎样算做完 / 失败怎么办 / 这次不做什么"（套用 SKILL.md 第 5 节门控模板）；新项目 / 新功能 / 新独立模块仍须做方案调研；交互效果存疑时不能调 prototype，改为文字描述决策并请用户确认。
   - ② 写成规格：按 SKILL.md 第 3 节四节模板（用户行为 / 约束 / 测试方法 / 范围外）在本地写 `docs/specs/<slug>.md`（可写简版，但四节必须齐）。
   - ③ 拆小任务：按"用户行为"纵向切片，逐票显式声明 Blocked by；无 to-tickets 协议时每票写一个 `.scratch/<slug>/issues/<NN>-<slug>.md`。
   - ④ 实现与验收：测试先行 → 运行真实测试并引用输出 → 自查 diff（替代 code-review 两轴）→ 请求人工走查。
   - ⑤ 复盘改进：按 SKILL.md 第 3 节阶段⑤ 三类（导航 / 自动化 / 规范）检查并列改进落点（可只列清单）。
3. 六处门控（访谈 / seam / 拆票 / 走查 / 复用决策）在降级态下仍必须停下等用户；并行升级默认关闭（无 implement-spec 协议即无 worktree 编排），除非用户明确要求且宿主支持。

**交接物**（质量下限——"必须产出"与"可省"分列）

- 必须产出：访谈澄清记录（问题 → 答案 → 依据）；简版规格（四节齐）；工单清单（每票含 Blocked by）；**真实测试输出原文**（引用，不编造；bug 修复类须含回归测试且真实通过）；未验证项清单；走查请求与用户确认记录。
- 可省（相对完整流程）：方案调研的完整候选分析（可收口为 1–2 次检索，或如实标注"未做方案调研"）；prototype 交互原型；domain-modeling 的 ADR / 词汇表；tracker 发布动作与标签；复盘改进的自动化落地（可仅列清单）。

**出口 checklist**

- [ ] 汇报首行已标注"已降级"并列出缺失技能 / 路径
- [ ] 五阶段最小步骤均已执行（可压缩，但六处门控与验收证据不可省）
- [ ] 简版规格四节齐（用户行为 / 约束 / 测试方法 / 范围外）
- [ ] 工单每票含 Blocked by，完成可判定
- [ ] 真实测试输出已引用，未验证项已列出
- [ ] 用户走查已请求并获确认

**常见失败**：把"已降级"藏着不标（用户误以为走的是完整流程）；拿降级当借口跳过门控或省略真实测试；缺失技能只报一个却漏报其余；用编造的测试输出充数。
