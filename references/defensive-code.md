# 编码：防御性代码决策

适用：写新代码、改代码、代码评审时，判断「这个防护该不该加、加在哪」——新增校验、判空、try/except、锁、默认值兜底等防御性代码；评审多层 try、同一条链路上反复判空时同样适用。

核心原则：复杂度按真实故障概率分配，判空和 try 都是成本。十行需求配百行防御，成本没有消失，只是从写代码的人转移给了所有读代码的人；放错层次，本该一次解决的问题会变成每次调用都要付一次。判断「加不加」看概率，判断「加在哪」看边界。

## 要不要加（决策规则）

1. **不为假想故障加复杂度**：不要为猜测出来、几乎不会发生的竞态或安全边界情况增加处理逻辑。
2. **要加先报账**：确实认为需要加，先说清三件事——具体会怎么出错、发生概率多大、要多写多少代码。得到同意再动手，不悄悄扩大改动范围。
3. **生成文件不手改**：自动生成的文件改源头后重新生成。
4. **按仓库现有流程走**：测试测真实实现，不把业务逻辑抄一份进测试，尽量少用 mock；不引入仓库没在用的工具或流程。

### 判断顺序

1. 这个防护针对的故障，实际出现过吗？没出现过且概率低，不加。
2. 必须加时加在哪一层？只加在数据入口。
3. 要写多少行？新增防护超过被保护逻辑本身的量级时，重新评估。
4. 用户没提、仓库也没先例？默认不加，先问。

## 加在哪（写法规则）

1. **判空只做一次，做在边界**：外部传进来的数据——参数入口、外部响应、文件与网络读取后——只在入口那一层校验一次。校验通过后，内部按已确定的类型直接使用，不再重复做防御性检查或重复判空。
2. **try 只包会失败的那一句**：不要把整个函数体塞进 try。只有一处 IO、解析或外部调用可能抛异常时，就只包那一处。
3. **一层能解决就不套第二层**：catch 里再 try，只在确实存在第二次失败可能时出现；否则合并分支或直接上抛。
4. **不吞异常**：捕获后必须做出选择——处理、转换后抛出、或记录并返回明确的失败结果。不允许空 catch，也不允许打完日志继续往下走。
5. **不加没有实测依据的并发防护**：没有共享可变状态、没有真实并发入口，就不加锁、不加「防并发」包装层。
6. **默认值要有业务含义**：给空值兜底只在业务上确实存在「空即默认」的语义时使用，否则让错误显式暴露。

## 改小功能时的常见反模式

- 新增一个字段，顺手把整条链路都补上 `if not x`。
- 一次 HTTP 调用被三层 try 包住，最外层只做 `pass`。
- 为了「防止并发」引入锁，但代码里根本没有并发入口。
- 给所有参数加默认值，把调用方的错误悄悄变成空值。

## 交付前自检

- 每处新增防护都能追溯到具体故障、明确要求或既有约定，而不是「万一」。
- 类型校验与判空只出现在入口，每个入口一次，内部没有重复检查。
- 每个 try 的作用域都是最小可失败单元，没有整函数包裹；没有空 catch，没有吞掉异常后继续执行。
- 新增的锁或并发结构，能指出具体竞争点与触发条件。
- 每个默认值都能说出对应的业务语义。
- 没有手改生成文件，没有引入仓库未使用的工具或流程。
- 测试针对真实实现，mock 的使用有明确理由。
